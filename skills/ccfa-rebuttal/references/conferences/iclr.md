# ICLR — Rebuttal 规则卡

> 标记：✅ 官方可查 · 🟡 社区经验 · ❓ 每年会变，**必须核对当年 review form**

## 一句话

OpenReview 上**完全公开**的讨论制。rebuttal 是「公开演出」：所有审稿人、AC 和未来的你在同一页面上看。
可以补实验、可以多轮、审稿人会明确回复是否改分。**这是最接近「谈判」的一种形态。**

## 关键参数

| 项目 | 值 | 标记 |
| --- | --- | --- |
| 平台 | OpenReview，review 与回复**全部公开**（非匿名读者也能看） | ✅ |
| 结构 | 每条 review 各一条 author response + 一条 global response（共性问题 / Summary of Changes） | 🟡 |
| 长度 | 通常无硬上限；实践上建议每条控制在几百到一千余词，长了没人读 | 🟡 |
| 富文本 | Markdown：表格、公式、列表全支持 | ✅ |
| 外链 | 允许但须匿名；匿名仓库镜像是常规做法 | 🟡 |
| 补新实验 | **允许且被强烈鼓励**，ICLR 社区普遍接受 rebuttal 期新结果 | ✅ |
| 修改论文 | 讨论期一般不重传 PDF，改动以文字承诺 + 后续版本落实 | ❓ |
| 讨论期 | 通常较长（数周），审稿人需明确回应是否改分 | 🟡 |
| 审稿人可见性 | 完全互相可见，且能看到彼此的讨论 | ✅ |
| 打分 | 分数 + 置信度；**刻度历年调整过**，直接看当年 review form | ❓ |
| 负分阈值（供 `--threshold`） | **6**（1–10 刻度时；若当年改为其他刻度，以 form 中 borderline 分之下为负） | 🟡 |

## ICLR 特有的三条

1. **公开性带来声誉成本。** 你在页面上的每一句都会被其他审稿人、AC，甚至一年后的读者看到。情绪化反击在 ICLR 的代价远高于纯文本会议。
2. **审稿人有义务回应。** 讨论期结束前，审稿人通常被要求给出是否改分的说明。所以**你的回复要写成「可被一句话确认」的形式**：
   `If the above addresses your concern about [X], we would appreciate an update to your score.`
   别写成需要他再读三段才能判断的散文。
3. **低分区间要单独对待。** 三个低分（如 333 这类分布）时，「什么都回答是是是」是最快出局的方式；此时目标转为**让 AC 看到「问题可解决」+ 至少一位审稿人态度松动**。松动一位，讨论区的风向就会变。

## 打法要点

- **先做「共性问题」再做单条**：ICLR 常见 4–5 位审稿人，重复回答同一质疑是纯浪费。
- **维护 Summary of Changes 并持续更新**，AC 写 meta-review 时几乎一定会引用它。
- **主动制造讨论**：点名 @ 审稿人请求确认，比等他来看更有效。
- **用表格压缩新实验**：ICLR 支持 Markdown 表格，这是它相对 AAAI 的巨大优势——把 4 行数字塞进一张表，比 400 字符的散文更有说服力。
- **对「要求与投稿后才出现的工作比较」**：指出时间线，说明属于 contemporaneous work，并承诺终稿引用。

## 常见坑

- 把公开讨论当私人辩论，越写越长，最后 AC 只看到「双方纠缠」。
- 只答负分审稿人，忽略正分审稿人 → 正分者被另一位审稿人的质疑带跑。
- 补实验不给对齐条件，被追问一句就很难看。
- 讨论期最后几天才动手 → 审稿人来不及改分。
