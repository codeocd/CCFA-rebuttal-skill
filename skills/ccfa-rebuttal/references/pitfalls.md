# 反模式清单与删减顺序

定稿前逐条对照。这一页的作用是拦住你本来会犯的错。

## 会直接掉分的动作

| 反模式 | 后果 | 正确做法 |
| --- | --- | --- |
| 把「打算做」写成「做了」 | 学术诚信问题，被抓到即拒 | 见 SKILL.md 时态表；未完成的写 `[待补证据]` |
| 编造 seed 数、p 值、延迟数字 | 同上 | 保留占位符，宁可空着 |
| 承诺「camera-ready 再补」却什么都没给 | 有记录：审稿人从 WR 直接降到 SR | 能给最小控制实验就先给，再承诺补全 |
| 通页 `We apologize` | 显得自己也不信这篇论文 | 结论先行，该争的争 |
| 复述审稿人的问题 | 白烧字符预算 | `Regarding W2 (latency):` 起头 |
| 只写「见对其他审稿人的回复」 | 有记录：唯一给正分的审稿人因此降分 | 写 `See Common Response C2 (Table below)` 并给一句话摘要 |
| 为省字数删掉某个被点名的 W | 讨论阶段被拿「漏答」当武器 | 合并同类项可以，静默省略不行 |
| 贴外链 / GitHub / 二维码 | 多数会议禁止，且破坏双盲 | 文字给参数，承诺终稿释出 |
| 承认 fundamental problem | 直接出局 | 承认 presentation，硬伤先核实再定性 |
| 在 Confidential Comment 里请求忽略某分数 | 「你在教我做事」 | 只请 AC 考虑评审质量 |
| 三位都低分时去申诉 | 基本无用，还浪费 AC 时间 | 正常回答 |
| 赌气撤稿 | 有 AC 反馈：之前撤过的稿子会被 desk reject；部分 ARR/OpenReview 流程还会限制重投 | 认真 rebuttal，领域很小 |
| 给正分审稿人写长回复 | Weak Accept 有 15.5% 概率被自己写崩 | 三句话封顶 |
| 用大词、长句、「高大上」措辞 | 越复杂越没人看 | 短句、简单词 |
| 情绪化反击（哪怕他真的很过分） | 其他审稿人和 AC 都在看你的体面 | 可以硬，不可以骂 |
| 向审稿人科普基础概念 | 像教训人 | 一句话给定位，指向论文 |
| 在 rebuttal 里加未被要求的新贡献 | CVPR 系明确告知审稿人可忽略新贡献，白烧字数 | 只答被问的 |

## 格式类坑

- **字符 ≠ 单词**：`apple` = 5 字符，空格、`|`、`-`、`#`、换行全部计费。1500 字符 ≈ 200–250 英文单词。
- 一张 Markdown 表格可能吃掉 300–500 字符。纯文本类会议优先用紧凑行。
- 各审稿人之间的字数**不能挪用**，所以「这位写得爽、那位来不及」是最常见的自伤。
- 提交框只收纯文本的会议：粘贴前先去掉 Markdown 渲染依赖（`**`、表格、脚注）。
- 页数限制的会议（CVPR 系 1 页 PDF）：超页或改页边距的 rebuttal **不会被读**。必须用官方 author kit 渲染后再数页。
- 双盲：不要出现 `our previous work [x]`，改 `Zhang et al. [x]`。

## 超字了？按这个顺序删

1. 所有对审稿人原文的复述（只保留 <=12 词的关键短语）。
2. 客套与收尾（整份只留一句总致谢）。
3. 形容词与副词（`very`、`significantly`、`clearly`、`thoroughly`）。
4. 括号里的补充解释——能删就删。
5. 表格 → 紧凑行（`latency: 12ms vs 18ms`）。
6. 次要/低置信度审稿人的长答 → 压成 2 句 + 指向共性问题。
7. 合并同类项成 Common Responses，各分回复只留指针。

**不许删**：被点名的每个 W/Q 的存在感、新实验的关键数字、具体承诺。

## 提交前 60 秒清单

- [ ] 每个 W/Q 都有对应回答，编号一致（`R1-W2` 风格）。
- [ ] 全文搜索 `will`，确认每个承诺都可核查（改哪段、加哪句、放哪张表）。
- [ ] 全文搜索 `[`，确认没有遗留未替换的占位符。
- [ ] 所有数字都能指到论文位置或 rebuttal 内给出的实测。
- [ ] 字符数：`node scripts/parse_reviews.mjs --check <workspace>` 全绿。
- [ ] 无外链、无身份泄露。
- [ ] 读一遍：一个没细读论文的 AC 能看懂吗？
